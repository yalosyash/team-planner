# Контракт раздельного хранения

Статус: этапы 1–3 задачи из [TODO](TODO.md) выполнены. Штатный сервер,
браузерный запуск и launcher используют раздельное хранение. Миграция выполняется
до загрузки интерфейса/запуска HTTP. Разработка и проверки не запускали перенос
рабочей data/. Полная доработка обмена/восстановления и общие критерии выпуска
остаются этапами 4–6.

## Реализация этапа 2 и её проверка

- `app/js/core/storage-schema.js`: общие дефолты, строгая проверка трёх форматов,
  ограниченные системные patch и канонический JSON для SHA-256.
- `lib/file-store.cjs`: `createFileStore(root)` без файловых операций при создании;
  `read`, `write`, `patch`, `updateLauncher`. Ревизия проверяется под межпроцессной
  блокировкой; временный файл синхронизируется и заменяет целевой через rename.
- `lib/storage-api.cjs`: `createStorageApi(root)` для трёх GET/POST-маршрутов
  из контракта. Подключён к `server.js`; все записи доски проходят общий
  писатель с проверкой ревизии и атомарной заменой.
- `app/js/core/split-storage.js`: браузерный адаптер с Web Locks и HTTP-адаптер
  без автоматического перехода на локальное хранение при ошибке записи.
  Подписка на `storage` сигнализирует об изменении категории; сама данные не заменяет.
- `.gitignore` и pre-commit защищают `settings/` и `runtime/`, включая принудительное
  добавление файлов. Эти правила не устанавливают хук автоматически.

Завершившийся владелец блокировки определяется по PID, но блокировка не удаляется
автоматически: иначе два процесса восстановления могут удалить lock нового
владельца. По тайм-ауту операция возвращает 503 с путём и PID; исходный JSON
сохраняется. Ручное удаление оставшегося lock допускается только после остановки
всех писателей. В браузере без Web Locks или Web Crypto чтение не создаёт ключи;
возвращает `readOnly: true`, а без Web Crypto также `revision: null`.

Проверки (Node.js 22.16.0; Chrome для второго теста):

```powershell
node --preserve-symlinks --preserve-symlinks-main tests/split-storage.mjs
node --preserve-symlinks --preserve-symlinks-main tests/split-storage-browser.mjs
```

Флаги preserve-symlinks обходят ограничение realpath в текущем Windows sandbox;
логику хранения не меняют. Первый тест проверяет настоящие временные файлы,
HTTP, конкурирующие процессы, ошибки write/rename, форматы, браузерный адаптер
и Git-хук в отдельном репозитории. Второй — две настоящие вкладки Chrome,
Web Locks, конфликты, события storage, перезагрузку и HTTP-адаптер.
Оба используют только временные каталоги/профили и удаляют их после завершения.
Проверка обычного чтения прежнего формата подтверждает отказ без перезаписи.

## Подключение этапа 3

`core/storage-migration.js` собирает и проверяет новые документы без I/O и
изменения исходного объекта. `core/task-migration.js` используется также штатной
загрузкой: группы уже преобразованных рабочих задач больше не сортируются
по `start`, версия 4 не понижается до 3. Пятидневка для действительно старой
календарной модели сохранена; загруженный календарь на это преобразование
не влияет, как и прежде. Необычно большая старая длительность свыше 100000 дней
останавливает подготовку с диагностикой, без изменения исходника.

`createFileStore(root).migrate()` получает блокировки миграции и трёх документов,
проверяет старый и новый PID, сохраняет точные исходники с SHA-256-манифестом
в отдельном уникальном каталоге, проверяет записи чтением. Preferences и system
записываются перед data, финальный маркер — последним. При повторной попытке
сохраняются уже перенесённые настройки; первоначальная копия остаётся доступной.
Живой/непроверяемый PID блокирует перенос; чужой процесс не завершается.

`createBrowserStore().migrate()` использует тот же преобразователь под Web Locks.
Точные строки прежних ключей и новых документов с контрольной суммой сохраняются
в `team-planner-migration-v1`; при повторной попытке эта копия не перезаписывается.
Ошибки quota/чтения/проверки прерывают операцию. Старый ключ удаляется только
после финальной отметки и сверки с точной копией; изменённый старой вкладкой
ключ не удаляется и предлагается для явного восстановления.

Проверки на временных каталогах и управляемом localStorage:

```powershell
node --preserve-symlinks --preserve-symlinks-main tests/storage-migration.mjs
```

Проверены очередь и рассчитанное расположение карточек, дробные длительности,
связи обмена, приоритет новых настроек, повторные/конкурирующие вызовы, отказы
записи на каждой фазе, повтор после этих отказов, повреждённые источники,
живой/невалидный PID и внешняя правка файла во время переноса. Chrome-тест выше
также проверяет миграцию в двух настоящих вкладках и повтор после перезагрузки.
Это не проверка внезапного отключения питания или принудительного убийства
процесса: при оставшемся файловом lock действует описанная выше диагностика
и ручное снятие блокировки после остановки всех писателей.

Сервер вызывает prepareInstallation до listen: получает instance.lock на всё
время работы, выполняет migrate, переносит журнал и удаляет проверенный мёртвый
старый PID. Launcher удаляется только при наличии точной копии этой попытки.
Если новый журнал уже существует и отличается от старого, старый остаётся
для диагностики. Новый PID записывается при listen и удаляется только своим
процессом при штатном завершении. Журнал ограничен 1 МБ. Второй обычный запуск
открывает найденный сервер; конкурентный старт не создаёт второго писателя.
Оставшийся instance.lock после аварийного убийства требует такой же ручной
проверки владельца, как блокировки отдельных документов.

start.bat находит Node до вызова VBS. VBS вызывает lib/launcher.cjs status/answer,
сама JSON не читает и не пишет. Сохранённый отказ или удаление ярлыка не вызывает
повторного вопроса. CLI при работающем новом сервере меняет только launcher под
общей системной блокировкой; незавершённая миграция при живом сервере блокируется.

core/storage.js загружает три документа и выставляет готовность только после
успешного чтения. Локальные свойства state — неперечисляемые обращения к настройкам,
поэтому сериализация доски не возвращает их в data. save сравнивает документы
отдельно; patch календаря повторяется после конфликта launcher только при отсутствии
пересечения изменённых секций. Конфликт самой доски не перезаписывается автоматически.
Несохранённые доски имеют отдельные recovery-ключи для каждой вкладки; сравнение
при восстановлении включает команду и не включает локальные настройки.

Старый сервер без storageVersion:4 и ошибка API блокируют загрузку/редактирование,
вместо перехода на пустую локальную доску. File-режим и явный HTTP 404 health
используют браузерный backend. Без Web Locks/Crypto исходники читаются без записи,
редактирование заблокировано, экспорт доступен; календарь фоном не обновляется.

Дополнительная проверка настоящего запуска, остановки и WSH с временным Desktop:

```powershell
node --preserve-symlinks --preserve-symlinks-main tests/installation.mjs
```

WSH/Chrome в текущем Windows sandbox могут требовать запуска теста вне sandbox.
Тесты используют отдельные временные данные, профили и Desktop; не запускают
штатный start.bat в рабочем каталоге.

## Границы и совместимость

Три независимых документа UTF-8 JSON; каждый имеет собственную версию формата.
Версия не является ревизией записи. Состояние интерфейса можно собирать в памяти
из трёх источников, но записывать его целиком в любой из файлов запрещено.
Порядок сотрудников, релизов и задач сохраняется: порядок задач задаёт очередь.
Идентификаторы и связи обмена сохраняются без генерации новых при миграции.

| Хранилище                   | Версия       | Владелец                      | Содержимое                                 |
| --------------------------- | ------------ | ----------------------------- | ------------------------------------------ |
| `data/data.json`            | `version: 4` | сервер / браузерное хранилище | доска и связи обмена                       |
| `settings/preferences.json` | `version: 1` | сервер / браузерное хранилище | тема, выбранный релиз                      |
| `settings/system.json`      | `version: 1` | общий модуль хранения         | календарь, launcher, уведомления, миграция |

Версия 4 отличает очищенную доску от старого смешанного формата 3.
`migrateTasks()` сохраняет версии 3 и 4; версия 4 выставляется преобразователем
формата хранения после проверки рабочей доски. Формат отдельного релиза остаётся версии 1.
Более новая неизвестная версия любого документа блокирует его перезапись:
показать ошибку совместимости, сохранить исходник. Повреждённый существующий
файл также не заменять значениями по умолчанию. Отсутствие и повреждение различаются.

## Рабочие данные

Пустая доска:

```json
{ "version": 4, "team": "", "people": [], "releases": [], "tasks": [] }
```

Разрешены только следующие поля, в том числе во вложенных объектах:

| Объект                     | Поля                                                                                                                                                      |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Корень                     | `version`, `team`, `people`, `releases`, `tasks`                                                                                                          |
| Сотрудник                  | `id`, `name`, `color`                                                                                                                                     |
| Релиз                      | `id`, `number`, `start`, `end`, необязательный `exchange`                                                                                                 |
| Задача                     | `id`, `releaseId`, `personId`, `start`, `days`, `type`, `number`, `title`, `status`, `link`, `labels`, `weekend`, `daysMode`, необязательный `exchangeId` |
| `exchange`                 | `origin`, `people`, `parents`, `base`, `sent`, `received`, `lastImport`                                                                                   |
| Элемент `exchange.people`  | `local`, `remote`                                                                                                                                         |
| Элемент `exchange.sent`    | `transferId`, `snapshot`                                                                                                                                  |
| Снимок `base` / `snapshot` | `release`, `tasks`                                                                                                                                        |
| Релиз внутри снимка        | `number`, `start`, `end`                                                                                                                                  |
| Задача внутри снимка       | поля задачи без `exchangeId` и `releaseId`; `id` и `personId` относятся к пространству обмена                                                             |

Снимки очищаются тем же явным списком рекурсивно. В частности, недостаточно
удалить `theme` из корня: произвольные свойства объектов не должны утекать
через spread. Семантика `exchange` соответствует `core/release-transfer.js`:
`base`, история отправки и родителей нужны для возврата и обнаружения конфликтов.
Лимит истории `sent` остаётся 20; миграция не должна обрезать другие связи.

`id` — непустая строка, уникальная внутри соответствующего массива.
`releaseId` и `personId` задачи ссылаются на существующие сущности.
Даты — существующие даты `YYYY-MM-DD`; конец релиза не раньше начала.
`days` — положительное конечное число; дробные дни сохраняются.
`type` — `task`, `vacation` или `sick`; `daysMode` — `work`.
`labels` — уникальные значения `FE`, `BE`, у отсутствий — пустой массив;
у отсутствий `weekend: true`. `status` — пустой, `waiting` или `preprod`.
Пустые `number`, `title`, `status`, `link` старых задач нормализуются без
потери содержимого; отсутствующий `labels` — `[]`. Ссылки проверяются существующим
`normalizeLink`. Не менять длительности или очередь в рамках разделения файлов.

Неизвестные поля старой доски сохраняются в исходной миграционной копии,
но не в новом рабочем документе или экспорте. Если известное рабочее поле
невалидно, остановить переход с диагностикой, а не молча удалить сущность.

## Личные настройки

```json
{ "version": 1, "theme": "light", "activeId": null }
```

`theme` — `light` или `dark`; `activeId` — строка или `null`.
Новая установка без выбора темы использует светлую. При миграции приоритет темы:
существующее новое поле → старая тема доски → старый ключ `team-planner-theme`
→ светлая. Для `activeId`: новое поле → старое → `null`.
Приоритет определяется наличием поля, а не truthiness: `null` и `false`
могут быть осознанными значениями.

После загрузки, импорта, удаления релиза или восстановления проверить `activeId`.
Существующий выбранный релиз сохранить; иначе выбрать первый в массиве;
если релизов нет — `null`. Исправление записывает только preferences.
До загрузки настроек старый ключ темы может служить кэшем для ранней отрисовки,
но после загрузки источником истины являются preferences.

## Системные данные

```json
{
  "version": 1,
  "calendar": { "years": {} },
  "launcher": {
    "desktopShortcutAsked": false,
    "desktopShortcutCreated": false
  },
  "queueNotice": false,
  "migrations": { "splitStorage": 0 }
}
```

`calendar.years` — объект с ключами годов 1900–2100. Значение года:
`{ "days": "…", "updatedAt": "ISO-8601", "source": "isdayoff.ru" }`.
`days` содержит 365/366 символов `0`, `1`, `2`, согласно `validYear()`;
`1` — выходной, `0` и `2` — рабочие. У старого валидного года без метаданных
не выдумывать время загрузки; метаданные допускается опустить.
При отсутствии года загрузить его штатным механизмом; при недоступности сети
сохранить валидный кэш, для неизвестного года использовать пятидневку.

Поля launcher — boolean. `Asked: true` означает, что повторно спрашивать нельзя,
включая отказ и удалённый пользователем ярлык. `Created` фиксирует результат
создания, а не текущее наличие `.lnk`. Существующий ярлык обрабатывается по
действующему сценарию без повторного вопроса.

`queueNotice` — boolean. Для старой доски перенести имеющуюся отметку; если
отметки нет, необходимость уведомления определяется старой моделью задач
до её преобразования. Для новой доски версии 4 и импорта уведомление о старой
очереди не показывать из-за отсутствия поля. `migrations.splitStorage` — 0 до
завершения перехода и 1 после; это отметка протокола, а не замена проверке файлов.

## Владелец записи и API

Один общий Node-модуль отвечает за валидацию, ревизии, блокировку и запись.
Сервер использует его напрямую. VBS не парсит и не записывает `system.json`:
после поиска Node вызывает отдельную CLI-команду того же модуля, передавая
только boolean-поля launcher. Порядок `start.bat` нужно изменить: проверить
Node до запуска обработчика ярлыка. CLI доступна и до запуска HTTP-сервера.

Для CLI и сервера обязательна одна межпроцессная блокировка записи system
в `runtime/`, взятая до чтения актуального файла. Очередь Promise внутри
сервера недостаточна. Под блокировкой перечитать документ, изменить только
разрешённую секцию, проверить и атомарно заменить файл. Проверять владельца
устаревшей блокировки; тайм-аут ожидания даёт явную ошибку без перезаписи.
Освобождать блокировку в `finally`; не удалять чужую блокировку.
Неизвестные секции system сохраняются при обновлении известной секции.

| Операция                | Контракт                                                                        |
| ----------------------- | ------------------------------------------------------------------------------- |
| `GET /api/data`         | `{data, revision}` только для доски                                             |
| `POST /api/data`        | `{data, baseRevision}`; полная проверка рабочего формата                        |
| `GET /api/preferences`  | `{data, revision}` личных настроек                                              |
| `POST /api/preferences` | `{data, baseRevision}` только личных настроек                                   |
| `GET /api/system`       | `{data, revision}` системных данных                                             |
| `POST /api/system`      | `{patch, baseRevision}`; из браузера разрешены только `calendar`, `queueNotice` |
| CLI launcher            | patch только `launcher`, под общей блокировкой                                  |

У каждого документа отдельный SHA-256 revision по сериализованному содержимому;
GET возвращает ревизию именно возвращённого документа. Отсутствующий data —
`null` с SHA-256 канонического `null`, настройки сначала создаются с дефолтами.
Проверка `baseRevision` и запись выполняются в одной критической секции.
Конфликт — 409, неверный документ — 400, ошибка диска — 500: успех и новый
revision возвращаются только после записи. Не делать автоматическую перезапись
при 409; удержать правки для явного разрешения пользователем.
Смена темы не конфликтует с правками доски; изменение launcher может потребовать
перечитать system и повторить patch календаря с проверкой пересечения изменений.

Писать во временный файл с уникальным именем в том же каталоге, закрыть его
и заменить целевой переименованием. Ошибка rename оставляет прежний документ;
fallback через copy поверх целевого файла запрещён. После записи перечитать
и проверить результат перед удалением миграционных исходников. Это гарантия
от частичной прикладной записи, не обещание сохранности при отказе накопителя.
Настройки и runtime не раздавать статикой; исключить из Git и защитных хуков.

## Браузерный режим

Те же документы и версии в отдельных ключах `team-planner-data-v4`,
`team-planner-preferences-v1`, `team-planner-system-v1`.
Старый `team-planner-v1` читать только для миграции/восстановления. Миграционную
копию хранить отдельно в `team-planner-migration-v1`, проверять чтением до
изменения старых ключей. При quota/security error остановиться без удаления
исходников. Сбой HTTP-записи не превращать незаметно в смену backend.

Вкладки сериализуют операции через Web Locks и проверяют ревизии внутри
блокировки. При отсутствии Web Locks разрешить чтение и экспорт, запись
блокировать с понятной причиной: localStorage не обеспечивает compare-and-swap.
Событие `storage` уведомляет о внешних изменениях, но не заменяет блокировку.
Браузерный кэш несохранённой доски отделить от preferences/system; успешная
запись доски не удаляет локальные настройки. Предложение восстановить копию
сравнивает рабочие данные, включая `team`, а не тему или календарь.

## Миграция, резервные копии и восстановление

1. Проверить отсутствие работающего старого сервера и получить блокировку
   миграции. Старый живой PID не удалять, неизвестный живой процесс не завершать.
2. Прочитать и проверить старые источники и существующие новые документы.
   До изменений сохранить точные байты `data.json`, `launcher.json` и имеющихся
   настроек в уникальный `settings/migration-backups/<id>/` с манифестом
   исходных путей, наличия файлов и SHA-256. Копия вне data намеренно содержит
   локальные сведения и не переносится вместе с доской. Проверить копии чтением.
   Не включать эти копии в ротацию обычных 20 версий.
3. Подготовить и проверить все три документа в памяти. Существующие новые
   поля приоритетны, недостающие дополнить старыми, затем дефолтами. До выставления
   дефолтов различать отсутствующий ключ и явно заданное новое значение.
4. Записать и проверить preferences и system, затем очищенный data. После этого
   записать `splitStorage: 1`. Частичный успех не считается завершением;
   повторный запуск использует сохранённые новые поля, исходники и манифест.
   Три файла не образуют атомарную транзакцию: до завершения приложение
   не принимает редактирование и не запускает фоновые сохранения.
5. Перенести старый журнал только при отсутствии нового. Старый PID не копировать;
   новый процесс пишет собственный PID после получения права запуска.
   Удалять старые launcher/log/PID только после подтверждённого переноса
   и проверки владельца PID. При ошибке оставить исходники и сообщить путь
   резервной копии; не продолжать старт с пустой доской.

Резервные копии имеют разные назначения:

| Вид                                              | Состав и восстановление                                                                      |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| `data/backups/`, автоматические и перед импортом | только доска версии 4; восстановление сохраняет окружение получателя                         |
| Аварийная копия перед импортом релиза            | актуальная доска из памяти, включая несохранённые правки; ошибка копирования отменяет импорт |
| Копия перед импортом всей доски                  | тот же принцип; сначала надёжная копия, затем замена                                         |
| Копия перед восстановлением                      | текущая доска; ошибка создания отменяет восстановление                                       |
| Старые версии из `data/backups/`                 | остаются читаемыми; при восстановлении выделяются только рабочие поля                        |
| `settings/migration-backups/`                    | точные исходники перехода; ручное восстановление при остановленном сервере                   |

Обычные снимки и экспорт никогда не содержат preferences/system. Исторические
смешанные бэкапы не переписывать: они могут содержать локальные поля до перехода;
их импорт и восстановление очищают эти поля. Поэтому перенос старой истории
может переносить исторические локальные сведения, но не применять их.

## Экспорт и импорт

Полный экспорт использует схему доски версии 4 и явные вложенные списки выше.
Отдельный релиз сохраняет существующий пакет `team-planner-release`, version 1:
`format`, `version`, `transferId`, `origin`, `exportedAt`, `parents`, `base`,
`release`, `tasks`, `people`. Пакет содержит только выбранный релиз, его задачи
и используемых сотрудников; поля снимков также очищаются по контракту.
Отдельного экспорта сотрудников сейчас нет: не добавлять новую функцию
в рамках разделения хранения. Сотрудники полного экспорта и пакета релиза
содержат только `id`, `name`, `color`.

При импорте полной доски старого формата извлекать только рабочие поля,
сначала выполнять существующие преобразования старых задач, затем формировать
версию 4. `theme`, `activeId`, `calendar`, `launcher`, `queueNotice` из файла
не применяются. Системная отметка миграции из импорта также не принимается.
При импорте релиза сохранить сопоставление людей, повторяемость импорта,
обнаружение конфликтов и происхождение из действующего протокола.
Календарь получателя влияет на размещение задач; пересчитанный `start` обычной
задачи не должен считаться конфликтующей правкой обмена. Даты отсутствий сохраняются.

## Проверки до переключения

Этапы 1–6 завершены; миграция подключена к штатному старту. Приёмка выполнена
на временных установках, рабочая data/ не мигрировалась. Перечень проверок
и команда запуска приведены в [QA-PLAN.md](QA-PLAN.md). При переключении проверены:

- Полное равенство рабочих полей и порядка до/после миграции, включая обмен,
  дробные дни, ссылки, FE/BE, отсутствия и выбранный релиз.
- Повторный старт и прерывание после каждой записи; ошибки чтения, rename,
  блокировки, повреждённый JSON, новая неизвестная версия и заполненный localStorage.
- Параллельные записи двух вкладок и CLI launcher: ни одна секция не теряется,
  устаревшая запись возвращает конфликт; два одновременных запуска не создают
  двух писателей одной доски.
- Полный и отдельный экспорт с подставленными лишними вложенными полями;
  старый/новый импорт, возврат релиза, повторный импорт и восстановление версий.
- Независимость ревизий и записей: тема → preferences, календарь/launcher → system,
  задачи → data; фоновые операции не возвращают локальные поля в доску.
- Недоступность файлов через HTTP, исключения Git и хуки; перенос одной data,
  корректный PID, ограничение журнала и браузерный режим.

Основания контракта: `app/js/core/storage.js`, `core/release-transfer.js`,
`core/calendar.js`, `core/theme.js`, `features/data-io.js`, `features/task.js`,
`features/release.js`, `features/calendar.js`, `server.js`, `start.bat`,
`create-shortcut.vbs` (пути JS относительно `app/js/`). `queueNotice` поддерживается
в системном хранилище и при миграции старых файлов; в обмен доской не входит.

### Реализация обмена и восстановления (этап 4)

Общая функция workingData выделяет рабочие поля на всех уровнях, включая
exchange/base/sent/snapshot. Полный импорт и восстановление сохраняют текущий
существующий activeId получателя, иначе выбирают первый релиз или null.
Импорт отдельного релиза явно выбирает импортированный релиз.

Перед заменой доски создаётся проверенная копия памяти. Ошибка резервирования
отменяет замену. /api/backup принимает максимум 5 МБ (байты UTF-8), очищает
локальные поля, проверяет рабочую схему, выполняет fsync и чтение результата.
/api/restore принимает { name, baseRevision }; проверка ревизии и снимок
текущего файла выполняются под блокировкой data. При конфликте — HTTP 409.
Исторические файлы остаются неизменными, очищается только результат чтения.
При изменении памяти во время ответа восстановления интерфейс сохраняет её
и предлагает экспортировать правки перед обновлением страницы.
