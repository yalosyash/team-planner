# План тестирования по справочнику продукта

## Основа ожидаемых результатов

Актуализация по справочнику: 10.11.2026, документация после объединения
в b3913ed и текущие дополнения. Источник ожидаемого поведения —
[справочник продукта](product/README.md), прежде всего UC/BR/UI/DM/ST/API/RUN.
Этот файл определяет, как проверять описанный результат, и не вводит
альтернативных продуктовых правил. Исходники помогают найти причину
расхождения, но не заменяют заранее заданное ожидание теста.

Для каждой проверки записывать: ID → точный раздел справочника → начальные
данные/экран → действие → ожидаемую реакцию и итог → уровень проверки →
тест/команду → фактический результат, ревизию и окружение. Для сохранения
проверять отдельно память, интерфейс, ответ записи и повторную загрузку.
Автоматизировано, прошло и принято — разные статусы. При расхождении
регистрировать дефект; менять справочник и ожидаемое значение можно после
согласованного изменения поведения, а не ради зелёного теста.

[Открытые вопросы](product/09-limitations-and-questions.md) не являются
готовыми продуктовыми требованиями. Для них допустимы исследовательские
проверки текущего результата; спорный результат не включать в приёмочный
барьер до решения. Исторический протокол — [PRODUCT-DOCS-CHECKS](PRODUCT-DOCS-CHECKS.md),
покрытие функциями — [F-01–F-46](product/10-traceability.md).

### Первый сквозной сценарий: заранее заданные результаты

Фикстура: пятидневка без праздников, релиз 16–20.11.2026, пустая доска.
Дата и календарь задаются тестом, а не берутся из реальной сети.

1. Открыть «Сотрудники», добавить Анну и ввести имя. До «Готово» доска
   и серверный JSON не меняются. Закрыть Escape: при повторном открытии
   Анны нет. Повторить добавление и нажать «Готово»: сотрудник появляется.
2. Создать релиз с датами выше: пять строк рабочих дней, Σ=0.
3. Добавить A=1.5 дня и B=0.5 дня: A занимает 16.11 и первую половину
   17.11; B — вторую половину 17.11; Σ=2 (EX-01).
4. Добавить отсутствие на целый день 16.11: A занимает 17.11 и половину
   18.11, B — вторую половину 18.11; Σ=3, рабочая часть=2.
5. Открыть задачу, ввести длительность 0, применить: «Время должно быть больше 0»,
   окно остаётся открытым; отмена сохраняет прежнюю длительность.
6. Дождаться «Сохранено», перезагрузить страницу, перезапустить изолированный
   сервер: сотрудники, релиз, длительности и порядок сохранились.
7. Экспортировать всю доску: проверить JSON v4 и отсутствие локальных полей.
   Импортировать в другую синтетическую установку: доска заменяется после
   резервирования памяти; тема/календарь получателя не заменяются.
8. Изменить доску и восстановить известную копию с подтверждением:
   восстанавливается содержимое копии, окружение сохраняется; перезагрузка
   подтверждает результат записи. Отдельно проверить отказ резервирования.

## Исторические результаты и существующие проверки

Историческая задача разделения хранения завершена; её результаты сохранены
в матрице и протоколе. Пустой TODO не является доказательством прохождения тестов. Это не закрывает все 16 шагов
общего QA-плана: Playwright/Vitest, GitHub Actions, бейдж и расширенные проверки
ниже остаются отдельной работой. Текущие тесты — самостоятельные Node-скрипты;
браузерные сценарии используют настоящий Chrome через CDP.

Проверенный локальный набор (Windows, Node.js 22.16.0, установленный Chrome;
для установки также нужен WSH):

```powershell
$checks = 'storage', 'calendar', 'calendar-auto', 'release-transfer', 'task-labels', 'updates', 'release-backup', 'storage-migration', 'split-storage', 'split-storage-browser', 'release-transfer-ui', 'installation'
foreach ($check in $checks) {
  node --preserve-symlinks --preserve-symlinks-main "tests/$check.mjs"
  if ($LASTEXITCODE -ne 0) { throw "Failed: $check" }
}
```

Это исторический набор проверок хранения, а не результат текущего прогона.
В протоколе справочника от 10.11.2026 два Chrome-теста остановились на
CDP timeout Runtime.enable; они не считаются успешно пройденными. Флаги preserve-symlinks нужны в текущем
Windows sandbox для обхода ограничений realpath. Chrome и WSH могут требовать
разрешения запуска вне sandbox. Проверки создают временные каталоги и
синтетические данные; `server.js` и `start.bat` из рабочей установки для них
не запускать — штатный старт уже включает автоматическую миграцию.

## Подход и инструменты

- Vitest: модульные тесты расчётов, интеграционные тесты состояния и хранения,
  управляемые часы, покрытие строк и ветвей.
- Playwright: браузерные сквозные сценарии, проверки реального HTTP API,
  скриншотные сравнения, сетевые ошибки и несколько вкладок.
- axe-core через браузерные тесты: автоматическая часть доступности.
- PowerShell: отдельные Windows-проверки start.bat, VBS и фонового процесса.
- Проверка синтаксиса JS — дополнительный быстрый барьер, не замена тестам.

Сохранить CommonJS для server.js и браузерные ES-модули. Не включать
"type": "module" в корне без отдельной оценки совместимости запуска.
Версии инструментов закрепить lock-файлом после проверки установленного Node.js.
Держать инструменты тестирования в devDependencies; обычный запуск приложения
должен по-прежнему работать без установки тестовых зависимостей.

- https://playwright.dev/docs/test-assertions

## 0. Изолированное окружение — обязательная основа

**Зачем нужен этап.** Подготовить безопасное и повторяемое место для запуска
всех автотестов на компьютере и в GitHub Actions. Каждый запуск получает
собственные вымышленные данные и сервер, поэтому тест удаления задачи или
восстановления версии не затронет рабочий план команды.

**Как используется.** Общие настройки поднимают приложение перед проверкой,
создают нужное начальное состояние и убирают временные файлы после завершения.

GitHub запускает те же проверки после push и показывает результат в бейдже.

случайно подключается к рабочему серверу, порт занят другим тестом или результат

пользовательских и остальных тестов; сама по себе она не проверяет функции продукта.

      совпадение цифр на доске с заранее рассчитанными примерами.
- [ ] Инварианты: сумма сегментов равна длительности для поддерживаемого
      диапазона; повторный repackAll не меняет результат; чужие очереди неизменны;
      обычные задачи не занимают запрещённые для них дни.
- [ ] Граничные входы: ноль, отрицательные/нечисловые значения, неверные даты,
      очень длинные диапазоны. Сначала определить ожидаемую реакцию на границе
      валидации; не закреплять случайный результат реализации как требование.

Ожидаемые даты и суммы задавать независимо от тестируемых функций. Не вычислять
ожидаемое значение тем же planPerson, который проверяется.

Готовность: все P0-примеры и инварианты проходят; предложенный целевой минимум
для dates/schedule/plan — 95% строк и 90% ветвей с разбором оставшихся пробелов.

## 2. Состояние, сохранение и миграции — P0

**Зачем нужен этап.** Убедиться, что действия пользователя сохраняются,
восстанавливаются после перезапуска и остаются корректными при обновлении
формата данных. Успешное появление карточки ещё не подтверждает запись на диск.

**Как используется.** Проверки меняют состояние, воспроизводят задержки и
ошибки сохранения, затем заново загружают данные и сравнивают результат.
Старые синтетические файлы проверяют переход на текущий формат. Часть сценариев
выполняется на уровне модулей, а ключевые циклы подтверждаются через браузер.

**Пример ошибки.** Пользователь дождался «Сохранено», закрыл вкладку, а после
открытия увидел старое значение. Закрытие до подтверждения записи — отдельная
исследовательская проверка, без гарантии доставки sendBeacon. Другой пример — индикатор показывает «Сохранено»,
хотя сервер отклонил запись. Этап проверяет весь путь состояния приложения;
работу HTTP-маршрутов и файлового механизма отдельно разбирает этап 3.

Модули: core/storage.js, keepalive.js, features/data-io.js, app/main.js.

- [ ] Первый запуск, пустой ответ сервера, корректные и повреждённые данные.
- [ ] Миграция старых длительностей и очередей; повторная миграция не меняет
      результат и не теряет поля. queueNotice проверяется как системное поле;
      миграционную плашку и кнопку «Понятно» не ожидать (Q-03).
- [ ] Отложенное сохранение объединяет быстрые правки; после перезапуска
      фактический JSON содержит последнее состояние.
- [ ] Медленный ответ, ошибка записи, отключение сети, восстановление связи;
      индикатор не сообщает об успехе раньше подтверждения записи.
- [ ] Изменение во время незавершённого сохранения: последние правки не теряются
      и не помечаются сохранёнными из-за ответа на предыдущий запрос.
- [ ] pagehide/sendBeacon и возврат страницы из истории; отдельно проверить
      итоговый файл реальным браузерным сценарием. Подтверждённая запись должна
      переживать закрытие; закрытие до «Сохранено» не имеет гарантии доставки.
- [ ] Серверная и браузерная копии, pendingLocal, выбор backend по ST-START-001,
      исключения доступа и переполнение хранилища. Ошибка серверной записи
      не вызывает fallback в localStorage; выбор recovery-копии — Q-15.
- [ ] Несколько вкладок: устаревшая ревизия даёт 409 и не затирает актуальную;
      экспорт памяти перед обновлением; никакого автоматического слияния.
- [ ] Экспорт → импорт сохраняет значимые поля, Unicode, дробные значения,
      ссылки и порядок очередей; тема, выбор релиза и календарь не входят
      в полный экспорт. Импорт сохраняет окружение получателя, выбор — по ST-EXCHANGE-001.
- [ ] Неверный JSON, структура, неизвестная версия, разорванные связи и
      дублирующиеся ID: отказ по UI-VALID-001/DM-CONTRACT-001 без замены доски;
      поддерживаемые старые версии преобразуются по DM-MIGRATION-001.

Готовность: сквозной цикл «изменить → сохранить → перезапустить → прочитать»
проходит, а ошибки сохранения и отката не скрываются от пользователя.

## 3. HTTP API и файловое хранение — P0

**Зачем нужен этап.** Проверить локальный сервер, через который браузер читает
и записывает план, получает версии и восстанавливает данные. Ошибка на этом
уровне может повредить файл даже при правильно работающих кнопках и формах.

**Как используется.** Тест отправляет настоящие HTTP-запросы тестовому серверу
и проверяет ответы и содержимое временных файлов. Запросы отправляются напрямую,
без кликов в браузере: так можно воспроизвести повреждённые данные, большой
запрос или недопустимый путь, которые обычный интерфейс не позволяет ввести.

**Пример ошибки.** Восстановление несуществующей версии затирает текущий план,
повреждённый запрос завершает сервер или файл из закрытого каталога доступен
по URL. Этап помогает определить, что причина сбоя находится на сервере.

Модуль: server.js. Интеграционные проверки используют настоящий HTTP и файловую
систему во временном каталоге; ошибки диска дополнительно воспроизводятся
управляемой подменой файлового адаптера.

- [ ] GET/POST /api/data, /api/preferences, /api/system: независимые ревизии,
      system patch только разрешённых секций; пустые данные, запись/чтение, типы ответов,
      некорректный JSON и структура, лимит тела, повторная и конкурентная запись.
- [ ] Неуспешная запись не повреждает предыдущий валидный файл; проверить
      запись во временный файл и rename; fallback через copy поверх живого
      JSON запрещён (ARCH-WRITE-001). Аварийные гарантии не расширять тестом.
- [ ] /api/backups: список, сортировка, метаданные, ротация до 20 снимков,
      интервал 15 секунд, снимок при запуске и перед восстановлением.
- [ ] /api/restore: успешное восстановление, неизвестное имя, неверный формат,
      повреждённый снимок, обход каталогов; ошибка не меняет текущие данные.
- [ ] /api/health, /api/alive, /api/bye: контракт и ошибочные запросы.
- [ ] Статика: HTML/JS/CSS/иконки, MIME, отсутствующий файл, недоступность data/,
      backups/, .git и исходников вне app/; обход путей, кодирование и неверный URL.
- [ ] Неверные методы, неизвестный API и ошибки: ожидаемые статусы/тела брать
      отдельно из API-STORAGE/OTHER/STATIC-001. У alive/bye нет строгого метода,
      неизвестный API доходит до статики. Устойчивость всех ветвей I/O —
      исследовательская проверка Q-17, не единый выдуманный контракт.
- [ ] Отдельно проверить запросы с чужим Origin и доступность по сетевым
      интерфейсам; согласовать границы локального доступа, затем закрепить контракт.

Готовность: все маршруты имеют успешные и негативные проверки; ошибки запросов
не повреждают данные и не обрушивают процесс. Проверки желаемой защиты,
которой пока нет, регистрируются как дефекты, а не подгоняются под текущий код.

## 4. Пользовательские сценарии — P1, критический smoke — P0

**Зачем нужен этап.** Проверить взаимодействие пользователя с программой:
можно ли выполнить нужную работу через реальные кнопки, поля, окна и доску.
Это основной этап для проверки приложения глазами пользователя и связывания
интерфейса, расчётов и сохранения в единый рабочий сценарий.

**Как используется.** Playwright открывает приложение в браузере, нажимает
кнопки, заполняет формы, выбирает сотрудника, подтверждает или отменяет действия.
Тест проверяет видимый результат, а при необходимости перезагружает страницу
или перезапускает тестовый сервер, чтобы подтвердить сохранность изменений.
Основные действия выполняются через интерфейс; подготовку исходных данных
можно ускорить фикстурами.

**Пример сценария.** Создать сотрудника → создать релиз → добавить задачу
на 1.5 дня → увидеть карточку и правильную загрузку → сменить исполнителя →
перезагрузить страницу → убедиться, что задача осталась у нового исполнителя.
Такой тест обнаружит неработающую кнопку или потерянное поле формы, даже если
отдельные расчётные функции и серверные запросы проходят свои проверки.

Короткий smoke-набор быстро проверяет, что основные действия вообще работают.
Полная регрессия охватывает остальные варианты, отмены и ошибки ввода.

- [ ] Команда: название, добавление/переименование/цвет/порядок сотрудников,
      удаление сотрудника с задачами: до «Готово» только черновик, после —
      общая доска и записи; Escape/крестик/фон отменяют все изменения окна.
      Палитра сначала закрывается отдельно. Основание — UC-PEOPLE-001.
- [ ] Релизы: создание, автоматический номер, даты, редактирование,
      переключение, удаление с задачами, последний и пустой релиз.
- [ ] Задачи: создание/изменение/удаление, исполнитель, дробная длительность,
      описание, номер, ссылка, статусы, «Работа в нерабочие дни»; валидация и отмена.
- [ ] Отпуск/больничный: дата, календарная длительность, смена типа,
      отсутствие видимых полей номера/ссылки/описания/статуса/меток,
      взаимодействие с очередью задач и сохранение после перезапуска.
- [ ] Доска: порядок людей, карточки, загрузка, перегруз, обрезка за релизом,
      штриховка, линия сегодня, длинные тексты, горизонтальная и вертикальная прокрутка.
- [ ] Ссылка открывается отдельно от редактирования карточки; опасные схемы
      блокируются; HTML из пользовательских полей отображается как текст.
- [ ] Модальные окна, палитра, подсказки: открытие/закрытие, Escape, клик снаружи,
      клавиатура, отсутствие перекрытия важных кнопок.
- [ ] Темы: переключение, сохранение отдельно от доски, первая отрисовка.
- [ ] Демо: при отсутствии людей заменяет массивы сразу, без подтверждения
      и резервирования; сохраняет команду/окружение (UC-DEMO-001).
      Проверить также состояние без людей, но с релизами; отмены после клика нет.
- [ ] Сквозные экспорт/импорт/версии через реальный сервер и реальные файлы.

Первый smoke-набор: запуск → сотрудник → «Готово» → релиз → задача → изменение →
перезагрузка с проверкой данных → экспорт/импорт → восстановление версии.
Каждый тест имеет собственные данные; результат не зависит от порядка запуска.

## 5. Жизненный цикл и Windows-запуск — P1

**Зачем нужен этап.** Проверить путь от запуска ярлыком до завершения фонового
сервера. Приложение должно открываться повторно без лишних процессов и оставаться
доступным, пока с ним работает хотя бы одна вкладка.

**Как используется.** Проверки запускают приложение в отдельной тестовой копии,
открывают и закрывают вкладки, воспроизводят занятый порт и проверяют созданные
процессы и PID-файл. Длительные интервалы сначала проверяются управляемыми часами,
а отдельные процессные сценарии подтверждают реальное поведение Windows-запуска.

**Пример ошибки.** Повторный запуск создаёт второй сервер, закрытие одной из двух
вкладок останавливает приложение для оставшегося пользователя или путь с пробелом
ломает ярлык. Обычный браузерный тест с уже поднятым сервером этого не обнаружит.

- [ ] Живая вкладка удерживает скрытый сервер; закрытие последней запускает
      ожидание остановки; новая вкладка отменяет остановку.
- [ ] Несколько вкладок, пропавшая вкладка, устаревшие ping, pageshow после
      восстановления: сервер не завершается при активном пользователе.
- [ ] Логику таймеров тестировать управляемыми часами; небольшой набор
      процессных проверок подтверждает реальный выход и очистку PID.
- [ ] start.bat/start-hidden.vbs: запуск, повторный запуск без дубликата,
      занятый порт, чужой процесс на порту, предел попыток, устаревший PID.
- [ ] Пути с пробелами и кириллицей, создание ярлыка, отсутствие Node.js,
      ошибки доступа: ожидаемый результат без зависших тестовых процессов.

Windows-сценарии выполнять в отдельной одноразовой рабочей копии/VM. Проверки,
требующие интерактивного рабочего стола, не выдавать за обычный headless CI.

## 6. Внешний вид, доступность и производительность — P2

**Зачем нужен этап.** Проверить, что работающими функциями удобно пользоваться:
карточки читаются, кнопки доступны, окна помещаются на экране, а большой план
не вызывает неприемлемых задержек.

**Как используется.** Визуальные тесты сравнивают снимки интерфейса с утверждёнными
эталонами. Проверки доступности ищут проблемы с подписями, контрастом и управлением
с клавиатуры. Прогоны в разных браузерах выявляют различия поведения, а нагрузочные
сценарии измеряют скорость на заранее заданных объёмах синтетических данных.

**Пример ошибки.** В тёмной теме не читается статус, длинное описание перекрывает
кнопку, диалог нельзя закрыть клавиатурой или добавление задачи на большой доске
надолго блокирует интерфейс. Тест создания задачи может пройти, если он проверяет
только факт появления карточки; этот этап оценивает дополнительные свойства.

Приоритет P2 определяет порядок внедрения набора. Если здесь обнаружена проблема,
блокирующая основную работу, её серьёзность оценивается по последствиям для
пользователя и не становится низкой из-за номера этапа.

- [ ] Скриншоты светлой/тёмной темы: пустая и заполненная доска, статусы,
      отсутствия, перегруз, линия сегодня, подсказки и основные диалоги.
- [ ] Фиксированные размеры: 1440×900, 1280×720 и 390×844 для проверки узкого
      окна; отдельно согласовать ожидаемое поведение мобильного интерфейса.
- [ ] Стабилизировать дату, шрифты, анимации и данные; эталоны привязать к ОС
      и браузеру. Обновление эталона — после просмотра различий.
- [ ] Автоматическая доступность: имена контролов, метки полей, контраст,
      семантика диалогов; сценарии клавиатуры и управления фокусом.
- [ ] Chromium — основной E2E; Firefox/WebKit — критические сценарии.
      Windows Edge — smoke фактического окружения, если установлен.
- [ ] Нагрузка на синтетических наборах: 10/30 сотрудников, 100/1000/5000 задач,
      несколько релизов и длинные периоды; измерить запуск, перерасчёт, отрисовку,
      сохранение, импорт. Большие наборы — исследовательские, не обещанный лимит.
- [ ] После базовых измерений задать бюджеты на фиксированном окружении;
      отслеживать деградацию, а не выбирать произвольные миллисекунды заранее.

Автоматизация доступности и скриншоты дополняются ручной проверкой удобства
и чтения с экрана; они не доказывают полную доступность интерфейса.

## Организация файлов и запусков

Предлагаемая структура: tests/unit/, integration/, api/, e2e/, visual/,
windows/, fixtures/, helpers/. fixtures содержит только синтетические данные.
Отчёты, traces, временные файлы и скриншоты падений исключаются из git;
утверждённые визуальные эталоны хранятся в репозитории.

- На каждое изменение: синтаксис, unit, интеграционные/API и Chromium smoke.
- На PR: полный Chromium E2E и относящиеся к изменению визуальные проверки.
- По расписанию или перед релизом: остальные браузеры, Windows, полный visual,
  негативные и нагрузочные сценарии.
- При падении сохранять имя сценария, seed/фикстуру, логи сервера, browser console,
  screenshot и Playwright trace. Не сохранять рабочие пользовательские данные.
- Не использовать фиксированные sleep для ожидания интерфейса; ждать состояния.
  Повторный успешный запуск после ошибки отмечать как нестабильность, а не скрывать.

## GitHub Actions и бейдж в README — обязательная часть этапа 0

Цель: после push тесты автоматически выполняются на GitHub, а в README сразу
виден результат проверок основной ветки. Локальный успешный запуск не заменяет
успешный прогон на GitHub.

- [ ] Создать `.github/workflows/tests.yml` с названием `Tests` и событиями
      `push` (во все ветки), `pull_request` и `workflow_dispatch` для ручного запуска.
      Не ограничивать обязательный workflow фильтрами путей.
- [ ] На каждом push выполнять весь реализованный обязательный набор:
      синтаксис, unit, интеграционные/API и Chromium E2E. По мере добавления тестов
      подключать их к workflow, а не оставлять только для локального запуска.
- [ ] Установка на чистом runner: checkout, согласованная версия Node.js,
      `npm ci` по lock-файлу, браузеры и системные зависимости Playwright.
- [ ] Отдельные jobs: расчёты/интеграции/API и браузерные тесты на Linux;
      автоматизируемые Windows-сценарии на Windows runner. Интерактивные сценарии,
      которым runner не подходит, показывать отдельно как оставшийся пробел.
- [ ] Визуальные тесты выполнять в том же окружении, где утверждены эталоны;
      дополнительные браузеры и нагрузку вынести в расширенный прогон по расписанию
      и перед выпуском. Основной бейдж отражает обязательный набор, не заменяет
      результат расширенного прогона.
- [ ] Ошибка теста, установки или запуска сервера должна делать workflow
      неуспешным. Не использовать `continue-on-error` для обязательных проверок;
      отсутствие найденных тестов не считать успешным прохождением набора.
- [ ] Добавить итоговый job `QA result`, который выполняется после всех
      обязательных jobs даже при их падении и проходит только при успехе каждого.
      Не допускать зелёного результата из-за пропуска зависимого job.
- [ ] Публиковать отчёты, coverage, логи, screenshots и traces при падении;
      задать таймауты jobs и срок хранения артефактов, например 14 дней.
- [x] Под заголовком README добавить кликабельный бейдж `Tests` для `main`
      и события `push`; ссылка открывает список запусков workflow.
      Бейдж добавляется вместе с рабочим workflow, а не до появления тестов.

Markdown будущего бейджа для текущего репозитория:

```markdown
[![Tests](https://github.com/yalosyash/team-planner/actions/workflows/tests.yml/badge.svg?branch=main&event=push)](https://github.com/yalosyash/team-planner/actions/workflows/tests.yml?query=branch%3Amain)
```

Бейдж показывает статус workflow основной ветки; результат push другой ветки
смотрят в Actions или проверках PR. Во время выполнения и до первого запуска
он может показывать промежуточный статус. Не обещать, что бейдж означает
прохождение тестов для любого открытого коммита или всех расширенных наборов.

Проверка готовности CI:

1. Push в тестовую ветку автоматически создаёт запуск, все обязательные jobs
   выполняются на GitHub без локальных файлов и пользовательских данных.
2. Намеренно сломанный тест в тестовой ветке делает workflow красным;
   артефакты позволяют определить причину. После исправления запуск зелёный.
3. После push рабочего workflow в main бейдж README отражает его реальный
   результат и открывает страницу запусков.
4. Инструкция в README объясняет локальный запуск и просмотр ошибок в Actions.

Дополнительно: при включении защиты main сделать `QA result` обязательной
проверкой перед слиянием. Это отдельная настройка репозитория: сам запуск
workflow не запрещает прямой push и не блокирует слияние автоматически.

Основание: [GitHub — статусные бейджи](https://docs.github.com/en/actions/how-tos/monitor-workflows/add-a-status-badge)
и [синтаксис workflow](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

## Критерии завершения и выпуска

Порядок работы задан единым чек-листом из 16 шагов в начале документа.
Разделы 0–6 раскрывают содержание этих шагов и используются для проверки полноты.

Для завершения каждой стадии: тесты проходят, сценарии связаны с точными
разделами справочника и группами QA-DOC-01–22,
обнаруженные расхождения зарегистрированы и имеют явное решение. Реальное время
оценить после первого вертикального smoke, когда известна стоимость изоляции.

Выпускной барьер сокращённого плана [С]:

- Реализован и проходит состав колонки [С] шагов 1–16; ручные проверки имеют
  записанный результат и окружение. Дополнения [П] перечислены как отложенные.
- Обязательный CI запускает существующие и новые проверки сокращённого набора;
  его реальный результат на GitHub подтверждён. Ручные проверки не выдаются за CI.
- Нет нерешённых дефектов потери данных, неверного планирования и блокировки
  основных действий; оставшиеся ограничения и пробелы явно описаны.
- Ожидания привязаны к справочнику; набор воспроизводим на чистой установке.
  Процент покрытия используется для поиска пробелов, без обязательного порога;
  требование 10 последовательных прогонов относится только к полному плану.

Предлагаемый выпускной барьер полного плана [С]+[П]:

- Все P0/P1-сценарии автоматизированы и проходят на согласованной матрице.
- Нет открытых дефектов потери данных, неверного планирования или блокировки
  основных действий; исключения принимаются явно с описанием последствий.
- Каждая текущая подсистема присутствует в матрице трассируемости.
- Для ядра достигнут целевой порог либо разобраны и обоснованы исключения.
  Общий процент покрытия — диагностическая метрика, не доказательство качества.
- Повторные чистые запуски стабильны; для проверки стабильности начальная цель —
  10 последовательных запусков критического набора без случайных падений.
- Любое исправление дефекта сопровождается воспроизводящей его проверкой;
  новые функции расширяют матрицу до включения в выпуск.

Неопределённые требования, которые нужно разрешать по мере реализации:
допустимые пределы данных/точности, частичная доступность при дробном отсутствии,
выбор recovery-кандидата, локальная HTTP-граница, поддерживаемые браузеры
и мобильный UX. Конфликт ревизий, схема и отказ неизвестной версии уже
описаны в справочнике и проверяются по нему.
Они не блокируют начало изоляции и тестирование известных расчётных сценариев.
