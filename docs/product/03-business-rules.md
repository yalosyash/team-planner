## BR-PLAN-001. Что задаёт положение задачи

Пользовательский путь: открыть карточку, изменить длительность или исполнителя,
нажать «Подтвердить». После закрытия диалога доска показывает пересчитанную
очередь. Дату начала обычной задачи в диалоге выбрать нельзя. Если ожидалась
другая дата, сначала проверьте предыдущие задачи, календарь и отсутствия
этого человека. Пошаговое взаимодействие —
[UC-TASK-001](02-scenarios.md#uc-task-001-добавить-или-изменить-работу).

Вход: даты релиза, исполнитель, порядок записей в `tasks`, тип, days,
weekend, даты и длительности отсутствий, доступный календарь. Для каждой
пары «релиз + человек» строится отдельная очередь обычных задач.
Источник порядка — массив, не номер задачи, статус или сохранённый start.
Отсутствия выбираются независимо от их места в массиве и исключаются из очереди.

Курсор начинается в дате начала релиза с занятостью 0. Задача использует
доступную часть дня; следующая продолжает с полученного курсора.
Если день заполнен, курсор переходит на следующий календарный день с 0.
Нерабочие дни/отсутствия пропускаются без расходования длительности;
при пропуске занятость сбрасывается на 0. Конец релиза не останавливает
раскладку. Обычная задача не может начаться раньше его начала.

Производный результат: участки `{i, amount, at}`, где i — номер календарного
дня от начала релиза (0 — первый), amount — работа в этом дне, at — начало
внутри дня. Рассчитанный start равен дате первого участка; он не хранит
дробную часть дня. Две задачи могут иметь одинаковый start без наложения.
Пример — EX-01. Основание: `core/plan.js: planPerson`,
`core/schedule.js: layoutFrom`.

## BR-PLAN-002. Дробные дни и точность

Рабочая ёмкость дня — 1. В доступном дне берётся
`amount = round(min(1 - at, left))`, затем обновляются left и at.
`round` округляет до двух десятичных знаков; сравнение завершения использует
EPS=1e-9. Интерфейс предлагает шаг 0.5, но схема допускает любое конечное
положительное число; вычисления начинают с `round(days)`.
Вне обычного ввода возможны расхождения: очень малая длительность может
округлиться в 0, тогда участков нет. Это ограничение, не согласованное правило
допустимости произвольной точности (Q-14).

Половины одного дня располагаются по вертикали, не в двух полных столбцах:
первая сверху, следующая снизу. Пропущенные дни внутри длинной карточки
занимают место на календарной сетке, но не тратят рабочую длительность.
Основание: `core/util.js: round`, `core/schedule.js: layoutFrom`,
`ui/board.js: renderCards, cardHTML`.

## BR-CALENDAR-001. Рабочие и нерабочие дни

При валидном загруженном годе код `1` означает нерабочий день, `0` и `2` —
рабочий. Сокращённый день не уменьшает ёмкость 1. Если валидного года нет,
рабочие дни — понедельник–пятница. Это выбор по каждому году отдельно.
Даты релиза включительны, норма считается по всему его периоду.

`weekend: true` («Работа в нерабочие дни») позволяет расходовать длительность
в любой день календаря, но **не отменяет отсутствие**. Режим одной задачи
не меняет календарную норму в шапке и не разрешает всем остальным работать
в выходные. Очередь остаётся последовательной: следующая задача не возвращается
заполнять пропущенные предыдущей выходные. EX-02/03/08.

Обновление календаря вызывает save/render и может сдвинуть очереди во всех
релизах, включая работу за их концом. Календарь получателя остаётся его
локальным календарём при импорте, поэтому одинаковые рабочие задачи могут
получить разные даты на разных установках. Основание: `core/calendar.js:
calendarWorkday`, `core/dates.js: workdaysBetween`, `features/calendar.js:
refreshCalendar`, `core/schedule.js: dayOff`.

## BR-ABSENCE-001. Отпуск, больничный и пересечения

Отсутствие раскладывается от собственной start по календарю с at=0,
без проверки других отсутствий. Его последняя дробь рисуется дробью.
Для исключения работы создаётся множество дат absent: каждый затронутый
календарный день блокируется целиком, даже при days=0.5 (EX-05).
Пересекающиеся отпуска/больничные объединяются по датам для блокировки,
но остаются отдельными записями и отдельно суммируются в Σ (EX-06).
Рабочая задача с weekend=true также пропускает эти даты.

В absent добавляются даты не раньше начала релиза; верхняя граница концом
релиза не ограничена. Поэтому отсутствие после релиза может сдвигать работу,
которая уже вышла за релиз. Карточка отсутствия целиком вне видимого периода
не показывается, но запись сохраняется и участвует в сумме (EX-10).
При частичном попадании показывается только видимая часть; отдельного
показателя «отсутствие за релизом» нет. Поведение дробного отсутствия
требует продуктового решения, см. Q-12.
Основание: `core/plan.js: absenceDates, planPerson`, `ui/board.js: renderCards`.

## BR-PLAN-003. Перерасчёт после правок

`render()` сначала вызывает `repackAll` по всем релизам/исполнителям,
записывает рассчитанные даты обычных задач в start и вызывает save при
изменении дат. Затем перерисовывает компоненты. Даты отсутствий не переписывает.
Раскладка карточек и загрузка каждый раз используют planPerson, а не доверяют
сохранённым start. Вызов previewPlacement — расчёт возможности размещения,
не показ пользователю отдельного расписания в окне задачи.

| Правка | Последствие | Основание / пример |
| --- | --- | --- |
| Увеличить/уменьшить days | Меняются конец текущей и начало последующих задач очереди | saveTask, layoutFrom; EX-09 |
| Удалить работу | Последующие занимают освободившееся место | deleteTask, render; EX-09 |
| Сменить исполнителя | Запись переносится в конец массива, в конец очереди нового человека; старая уплотняется | saveTask, previewPlacement; EX-09 |
| Изменить порядок массива | Меняется порядок рабочей очереди; UI-команды перестановки задач нет | planPerson; EX-09 |
| Изменить начало релиза | Очередь строится с нового начала; отпуск остаётся на собственной дате | repackAll, saveRelease; EX-09 |
| Изменить только конец релиза | Рабочие участки не сдвигаются, меняются видимая область, норма и показатель выхода | planPerson не использует end для раскладки; EX-01/07 |
| Перенести/удлинить отсутствие | Меняется множество заблокированных дат и последующая работа | absenceDates; EX-04/09 |
| Сменить тип | Обычная запись включается/исключается из очереди; при том же человеке позиция массива остаётся | saveTask; UC-ABSENCE-001 |
| Изменить статус/FE/BE | Рабочие участки и нагрузка не меняются | planPerson/layoutFrom не читают эти поля; EX-09 |
| Обновить календарь | Пересчёт рабочих дат и нормы | refreshCalendar; EX-08 |

## BR-LOAD-001. Показатели в шапке

После добавления/правки карточки посмотрите на Σ под именем человека.
Наведите на него указатель: подсказка показывает длительность обычных задач,
норму периода и отдельно отсутствия. Если рядом есть «+N дн за релизом»,
часть работы не помещается. Чтобы изменить её, нажмите соответствующую
карточку, исправьте длительность/исполнителя и подтвердите — показатели
будут рассчитаны заново. Ни статус «Готово», ни закрытие подсказки их не уменьшают.

Пусть all — **все записи** человека в выбранном релизе, в том числе за
его датами. `round(x)` — округление до сотых.

| Показатель | Фактическая формула |
| --- | --- |
| Σ X дн | `fmtDur(sum(all.days))`; fmtDur округляет для подписи |
| Рабочая длительность W | `round(sum(days обычных задач))` |
| Отсутствия R в подсказке | `round(sum(all.days) - W)` |
| Норма N | Количество рабочих дат в [release.start, release.end] по локальному календарю |
| Красный Σ | `W > N + 1e-9` |
| +O дн за релизом | `round(sum(overflowDays(queue.segs)))`, только обычные задачи |

Норма не уменьшается на отпуск/больничный, W включает готовые задачи и работу
в выходные. Σ не является числом занятых рабочих дней внутри релиза: в него
входят календарные отсутствия, пересечения и вся длительность за границами.
Поэтому при EX-04 есть выход работы без красного Σ, а при EX-03 красный Σ
есть без выхода работы. Красный показатель и выход отвечают на разные вопросы.
Основание: `ui/board.js: renderHeads, personOutflow`, `core/plan.js: overflowDays`.

## BR-LOAD-002. Загрузка по дням и дневная перегрузка

Для каждой обычной задачи берутся участки planPerson; для каждого i≥0
`load[i] = round(load[i] + amount)`. Отсутствия не добавляются.
Отображаются только даты релиза. Ячейка красная при `load[i] > 1.001`.
Половины двух задач дают 1, а не перегрузку. Выходные с разрешённой работой
тоже имеют порог 1, независимо от нормы N.

Обычная текущая очередь последовательно распределяет ёмкость ≤1; в проверенных
примерах дневной перегрузки нет, даже при красном Σ. Код умеет рисовать красный
фон, но воспроизводимый допустимый ввод, порождающий load>1.001, не установлен.
Не следует обещать пользователю, что превышение длительности релиза обязано
создать красные дни. Вопрос Q-13. Основание: `core/storage.js: personLoad`,
`ui/board.js: renderBodies`.

## BR-BOUNDARY-001. Выход за конец и ограничения

Для D=`diffDays(start,end)+1` суммируются amount участков с i≥D.
Количество дней за релизом — рабочая длительность, не разница календарных дат.
Работа, частично выходящая за период, обрезается при отрисовке и получает
пунктир. Целиком вышедшая работа получает условную карточку в последнем дне,
чтобы её можно было открыть. Этот условный участок не добавляется в personLoad.
Отсутствие целиком вне периода такой карточки не получает. EX-07/10.

Раскладка одной записи и построение отсутствий ограничены 2000 итерациями
календарного цикла. Пропуски тоже расходуют итерации. Для входа A=2001
с weekend=true фактически получены только 2000 участков: сумма сегментов
не всегда равна введённой длительности. Ошибки пользователю на этой границе
layoutFrom не выдаёт. Это ограничение Q-09, а не приемлемый диапазон задачи.

## Проверенные примеры

Во всех примерах один человек p и один релиз r, задачи идут A, затем B.
Если не оговорено другое, календарь пустой (fallback пятидневки),
weekend=false, все даты — 2026 год. `дата:amount@at` — участок работы.
Колонка «красный» относится к Σ. У всех примеров дневная перегрузка отсутствует.

| ID | Вход | Размещение | Σ / N / красный / O | Объяснение |
| --- | --- | --- | --- | --- |
| EX-01 | Релиз 16–20.11; A=1.5, B=0.5 | A:16.11:1@0,17.11:0.5@0; B:17.11:0.5@0.5 | 2 / 5 / нет / 0 | Остаток дня получает следующая задача |
| EX-02 | 20–23.11; A=2 | 20.11:1,23.11:1 | 2 / 2 / нет / 0 | Сб/вс пропущены |
| EX-03 | 20–23.11; A=3, weekend=true | 20,21,22.11 по 1 | 3 / 2 / да / 0 | Работа помещается за счёт выходных, норма остаётся 2 |
| EX-04 | 16–20.11; A=5, отпуск 18.11=1 | A:16,17,19,20,23.11 по 1 | 6 / 5 / нет / 1 | Отсутствие не уменьшило норму, но сдвинуло работу |
| EX-05 | 16–20.11; A=1, отпуск 16.11=0.5 | A:17.11:1 | 1.5 / 5 / нет / 0 | Полдня отсутствия блокирует весь день |
| EX-06 | 16–20.11; A=1, отпуск 16.11=2, больничный 17.11=2 | A:19.11:1 | 5 / 5 / нет / 0 | Блокируются 16–18.11, длительности отсутствий суммируются как 4 |
| EX-07 | Только 16.11; A=1.5, B=0.5 | Те же участки, что EX-01 | 2 / 1 / да / 1 | A частично за периодом, B целиком за ним |
| EX-08 | 20–21.11; A=1; искусственный календарь: 20.11=1, 21.11=2 | A:21.11:1 | 1 / 1 / нет / 0 | Рабочая сокращённая суббота имеет ёмкость 1 |
| EX-10 | Только 16.11; A=1 weekend=true; отпуск 17.11=1 | A:16.11:1, отпуск за видимой доской | 2 / 1 / нет / 0 | Σ учитывает невидимое отсутствие |

EX-08 не является сведением о настоящем производственном календаре России.
Скрипт явно задаёт искусственный год и не обращается в сеть.

EX-09 проверяет изменения отдельно на релизе 16–20.11 с A=1, B=1:

| Изменение входа | Проверенный результат |
| --- | --- |
| Без правок | A начинает 16.11, B — 17.11 |
| A=2 | B начинает 18.11 |
| Порядок B,A или удаление A | B начинает 16.11 |
| Начало релиза 17.11 | A начинает 17.11 |
| Отпуск 16.11 → перенос на 17.11 | Начало A: 17.11 → 16.11 |
| A переносится к q после Q=2 | previewPlacement даёт 18.11; B у p начинает 16.11 |
| У обеих задач устаревший start=01.12 | repackAll записывает 16/17.11; второй вызов изменений не делает |
| Статус Готово и обе метки | Участки равны исходным |

Проверки изменения входов вызывают расчётные функции, а не кнопки интерфейса.
Факт перемещения записи при смене исполнителя основан также на чтении saveTask.
