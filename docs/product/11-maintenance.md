# Как поддерживать справочник

Точка входа для читателя — [указатель вопросов](README.md#найти-ответ-по-действию-или-вопросу).
Справочник описывает ревизию и предел проверки, указанные на входной странице.
Наличие описания не означает, что все его ветви пройдены в браузере.

## Где находится основное описание

У каждого вида сведений один основной раздел. В остальных главах достаточно
кратко назвать следствие и дать ссылку; формулы, лимиты и алгоритмы целиком
повторять не нужно. Повтор названия кнопки в пошаговом сценарии допустим:
сценарий должен оставаться понятным без чтения исходников.

## Порядок обновления при изменении поведения

1. Указать ревизию и затронутые F/UC/BR/UI/DM/ST/API/RUN-идентификаторы
   в матрице. Существующие идентификаторы сохранять; удалённые не переиспользовать.
2. Проверить реализацию и подписи интерфейса. Обновить основной раздел
   из таблицы и связанные сценарии: исходный экран → действие → реакция →
   наблюдаемый результат. Проверить ошибку и отмену там, где они применимы.
3. При изменении расчёта обновить правило и конкретный пример входа/результата.
   При изменении данных проверить связи, обмен, миграцию и восстановление.
4. Выполнить подходящую проверку на синтетических данных. Записать окружение,
   команду или шаги, результат и оставшиеся ограничения. Чтение кода,
   пройденный тест и ручное наблюдение указывать раздельно. Сбой подключения
   теста не считать успехом проверяемого сценария.
5. Обновить матрицу, указатель вопросов, перекрёстные ссылки, дату и ревизию
   входной страницы. Удалить устаревшие обещания будущих разделов.
6. Проверить локальные ссылки и якоря, термины по словарю и пробелы в diff.
   Для документационной правки без изменения поведения повторный запуск
   приложения не требуется.

Ожидаемое поведение изменять после принятого продуктового решения. Исправление
приложения и отметку о прохождении проверки не подменять правкой текста.
Отдельные указания пользователя о размещении сведений имеют приоритет.

## Шаблон описания функции

Для нового сценария укажите назначение и точку входа, предусловия,
шаги взаимодействия, ошибку и отмену, связанные правила и результат.
Добавьте конкретный пример, источник реализации, ревизию, дату и способ
проверки. Открытые вопросы и пределы проверки обозначьте явно.

Пишите сначала на языке пользователя: экран и элементы → действие → реакция →
наблюдаемый результат. Технические детали объясняют этот путь. Сверяйте подписи
с разметкой и обработчиками; прежние документы не заменяют проверку кода.
Используйте синтетические данные, без копирования рабочих досок и настроек.
Планы из TODO/QA не считайте реализованными функциями или пройденными тестами.

## Устройство документации

Основные сведения находятся в README проекта и главах этого справочника.
Завершённый план подготовки, прежнее руководство GUIDE и отдельный контракт
STORAGE-FORMATS удалены после объединения 10.11.2026. История этих документов
сохраняется в Git, например в ревизии 4ca7347. Протокол проверок, исходный
срез, открытые вопросы и QA-план остаются отдельными: у них другое назначение.
