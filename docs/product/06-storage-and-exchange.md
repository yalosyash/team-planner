## ST-START-001 — откуда появляется доска

| Исходное состояние | Действие | Реакция | Результат |
| --- | --- | --- | --- |
| Приложение ещё не открыто | Запустить `start.bat` | Подготовка установки, затем браузер; индикатор «Загрузка данных…» | Через HTTP загружаются доска, настройки и системный документ |
| Страница открыта с `file:` или `/api/health` вернул 404 | Открыть приложение | Выбирается браузерное хранилище | Индикатор «Хранение: в браузере»; данные принадлежат этому браузерному хранилищу |
| Сеть недоступна, API вернул ошибку или неподдерживаемую версию | Открыть страницу | Красный статус, текст «Не удалось загрузить данные: …», элементы ввода отключены | Пустая браузерная доска вместо серверной автоматически не открывается |
| Браузеру недоступны Web Locks или Web Crypto | Открыть браузерную доску | Статус «Только чтение и экспорт: нет Web Locks / Web Crypto» | Доска недоступна для взаимодействия; остаётся полный экспорт |
| Найдена отличающаяся локальная копия | Прочитать стартовое подтверждение | OK предлагает загрузить браузерные данные с перезаписью файла; «Отмена» оставляет загруженную доску | При OK копия заменяет доску в памяти и ставится на сохранение; это не слияние |

Проверка сервера требует `storageVersion: 4`. Затем последовательно читаются
`data`, `preferences`, `system`. Отсутствующая доска даёт пустую модель; отсутствие
настроек допускает значения по умолчанию, повреждённый существующий документ — ошибку.
Активный релиз проверяется по существующим: при неверном ID выбирается первый.

Локальные кандидаты: ключи несохранённых досок `team-planner-unsaved-v4:*`,
в серверном режиме ещё `team-planner-data-v4`, затем старый `team-planner-v1`.
Предлагается первый отличающийся кандидат, без сортировки по `savedAt` и без
сравнения дат свежести. Надпись про `data.json` используется и в браузерном режиме.
Отказ сам по себе не удаляет найденную копию; успешное последующее сохранение
очищает предложенный ключ. Повреждённый JSON кандидата может прервать загрузку:
это ограничение, а не гарантированная автоматическая починка.

Основание: `core/storage.js:initStorage`, `app/main.js:start`,
`core/split-storage.js:read`, `lib/file-store.cjs:load`.

## ST-SAVE-001 — как понять, что изменения сохранены

| Что видно | Действие пользователя | Реакция и наблюдаемый результат |
| --- | --- | --- |
| Открыта доска | Изменить задачу, сотрудника, релиз или настройки | Меняется состояние/отображение, индикатор «Сохранение…»; последняя правка откладывает запись на 500 мс |
| «Сохранение…» | Дождаться ответа хранилища | После всех успешных операций — «Сохранено» на сервере либо «Хранение: в браузере» |
| Красная ошибка записи | Сохранить полный экспорт через меню экспорта | Скачивается текущая доска из памяти; это способ сохранить правки отдельно от недоступного хранилища |
| «Нет подключения — данные не сохранены» | Вернуть доступность сервера, оставить вкладку открытой | Успешный сигнал жизни повторяет запись несохранённых данных; только успешная запись подтверждает сохранение |
| «Данные изменились в другой вкладке — обновите страницу» | Сначала экспортировать нужные правки, затем обновить страницу | Перечитывается актуальное хранилище; автоматического объединения досок нет |
| Есть несохранённые изменения | Закрыть/перезагрузить вкладку | `pagehide` пытается отправить запись и оставить локальную аварийную копию; подтверждения доставки уже нет |

Уведомления «Данные загружены», «Релиз импортирован» и подобные означают
применение операции в памяти. Смотрите также индикатор сохранения.
Отдельной кнопки принудительного повторения записи в UI нет.

Записываются только изменившиеся документы, каждый со своей исходной ревизией.
Операции трёх документов выполняются параллельно: общей транзакции между ними
нет, поэтому часть могла сохраниться при ошибке другой части. Новые правки во
время записи вызывают следующий проход. Конфликт 409 блокирует соответствующий
документ до перечитывания, обычная сетевая ошибка — нет. Для системного patch
разрешена одна повторная попытка с новой ревизией, если чужая правка затронула
другую секцию (например, ответ launcher про ярлык).

В серверном режиме сигнал жизни идёт сразу и каждые 30 секунд; после двух
неудач подряд появляется сообщение об отсутствии подключения. Восстановление
связи при несохранённых правках вызывает `persistServer`. У браузерного режима
такого таймера повторной записи нет: следующая правка снова вызывает сохранение.

На `pagehide` при уже выполняющейся записи не отправляется её дубликат.
Иначе сервер получает `sendBeacon` с исходной ревизией. Лимиты браузера,
аварийное завершение и отсутствие ответа не дают гарантии записи. Аварийный
кэш содержит только доску, не отдельные настройки; ошибки его записи
подавляются. Перед важным закрытием дождитесь успешного статуса.

Основание: `core/storage.js:markDirty/persist/writeSystem/flush/cacheBoard`,
`core/keepalive.js:ping`. В приложении подписка браузерного адаптера на события
`storage` не подключена к автоматическому обновлению state: другая вкладка
обнаруживается при записи по ревизии, а не как синхронное совместное редактирование.

## ST-FILES-001 — где находятся данные и какие копии существуют

| Назначение | Серверная установка | Браузер |
| --- | --- | --- |
| Рабочая доска v4 | `data/data.json` | `team-planner-data-v4` |
| Тема и активный релиз v1 | `settings/preferences.json` | `team-planner-preferences-v1` |
| Календарь, launcher, маркер миграции v1 | `settings/system.json` | `team-planner-system-v1` |
| История доски | `data/backups/data_*.json`, максимум 20 распознаваемых копий | Одна копия `team-planner-release-backup` перед заменой |
| Исходники миграции | `settings/migration-backups/<UUID>/` с manifest и SHA-256 | `team-planner-migration-v1` с исходными строками и контрольной ревизией |
| Несохранённая доска | Локальный ключ `team-planner-unsaved-v4:*` в браузере, даже при сервере | Такой же локальный ключ |
| Процессы и диагностика | `runtime/`, см. [запуск](08-runtime.md) | Не часть переносимой доски |

Ревизия — SHA-256 канонического JSON, а не счётчик или дата. Запись файла:
блокировка документа, проверка ревизии, временный файл с уникальным именем,
`fsync`, закрытие, `rename`. Неудачный rename не заменяется копированием поверх
живого JSON. Блокировка ждёт до 2 секунд; оставшийся lock автоматически не
удаляется. В браузере используются Web Locks и атомарная запись одного ключа
localStorage; ошибка квоты оставляет прежнее значение этого ключа.

Сервер делает принудительный снимок существующей доски при запуске, перед
восстановлением и снимки **предыдущей дисковой** доски перед записью не чаще
раза в 15 секунд. Отдельный `/api/backup` сохраняет присланную доску **из памяти**
перед заменой. При ошибке создания обязательной копии соответствующая операция
не продолжается. Ротация общая для этих распознаваемых файлов; список UI
сортируется по имени, удаление старых копий — по mtime. Это не история каждой правки.

## ST-EXCHANGE-001 — что заменяет перенос данных

| С экрана | Действие и реакция | Последствия и отмена |
| --- | --- | --- |
| Меню экспорта | Полный экспорт скачивает JSON, уведомление «Файл сохранён» | Доска остаётся прежней; файл содержит рабочую доску без темы, активного релиза и системных настроек |
| Меню импорта | Выбрать полный JSON до 5 МиБ; проверка, копия текущей памяти, «Данные загружены» | Заменяются вся команда, люди, релизы и задачи. Отдельного подтверждения замены нет; отменить можно в выборе файла до чтения |
| Выбор релиза для экспорта | Выбрать релиз и экспортировать | В файл входят релиз, его задачи и люди с задачами; в исходной доске обновляются метаданные обмена и запускается сохранение |
| Импорт релиза | Выбрать файл до 10 МиБ; появляется предпросмотр, сопоставление людей, предупреждения | До применения доска не меняется; для замены нужен флажок. Повторный пакет блокируется, старый/параллельный предупреждает |
| Предпросмотр релиза | «Добавить релиз» / «Заменить релиз» | Проверяется сопоставление, создаётся копия всей текущей доски; применяется только релиз и необходимые связи людей, остальные релизы сохраняются |
| Пустое по сотрудникам состояние с демо | Загрузить демонстрацию | Массивы людей, релизов и задач заменяются без подтверждения и предварительной копии; название команды остаётся |

Подробные подписи и шаги: [полный обмен, релиз, восстановление, демо](02-scenarios.md).
Импорт проверяет/мигрирует модель перед заменой. Сбой резервирования отменяет
замену. Изменение доски во время резервирования также отменяет её, хотя копия
уже могла появиться. У релизного предпросмотра есть отдельная проверка устаревания;
закрытие окна до окончания резервирования не применяет пакет.

## ST-RESTORE-001 — как вернуть доску

Откройте резервные копии: в серверном режиме сначала «Загрузка…», затем строки
с датой, временем, числом релизов/задач и кнопкой «Восстановить». Нажмите кнопку,
прочитайте подтверждение замены всей доски. «Отмена» оставляет её прежней.
При подтверждении резервируется текущая память, сервер дополнительно сохраняет
предыдущее дисковое состояние и пишет выбранную копию с проверкой ревизии.
При успехе окно закрывается, появляется количество восстановленных релизов и задач.
Тема и системные настройки не откатываются.

Если файл уже удалён ротацией, список обновляется с предложением выбрать другой.
При конфликте/ошибке выводится «Не удалось восстановить: …». Если локальная
доска изменилась во время серверного запроса, сервер уже мог восстановиться,
но память не заменяется: сообщение просит экспортировать правки перед обновлением.

В браузере показывается одна копия перед последней заменой и кнопка
«Восстановить». Подтверждение сначала сохраняет текущую доску в этот же ключ,
затем загружает прежнюю: копия меняется местами с текущим состоянием, а не
накапливает историю. Без копии показывается сообщение о недоступности копий
без серверного запуска. Подробный путь — [UC-RESTORE-001](02-scenarios.md).

## ST-MIGRATE-001 — переход старой установки

Миграция происходит автоматически при подготовке установки до HTTP, а в
браузере до чтения рабочих документов. Пользователь не нажимает кнопку
преобразования. После успешного старта видит прежнюю доску в текущем формате;
при ошибке старт останавливается с сообщением, а не заменяет её пустой доской.

Преобразуются старые версии доски, локальные настройки отделяются от рабочего
JSON, ответ о ярлыке переносится из старого launcher. Точные поля —
[DM-MIGRATION-001](05-data-model.md). Файловая миграция сначала проверяет PID,
снимает байтовые копии исходников и manifest, проверяет неизменность источников,
затем пишет preferences, system с маркером 0, data, system с маркером 1.
Это последовательность с возможным частичным завершением, а не единая транзакция.
Каждая запись перечитывается и проверяется; путь к копии добавляется к ошибке.
Исходники для ручного восстановления нельзя смешивать с обычными копиями доски.

Браузер аналогично сохраняет исходные строки с контрольной суммой, проверяет
старые ключи перед записью и ставит конечный маркер последним. Старый ключ
доски удаляется только при совпадении с проверенной копией. Старый ключ темы
может сохраняться как зеркало для раннего оформления страницы.

Основание разделов: `features/data-io.js`, `features/release-transfer.js`,
`features/demo.js`, `core/storage-migration.js`, `core/split-storage.js`,
`lib/file-store.cjs`, `lib/file-migration.cjs`, `lib/installation.cjs`, `server.js`.
Протокол выполненных проверок — в [матрице](10-traceability.md).
