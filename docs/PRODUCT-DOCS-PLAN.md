# План подготовки технического описания продукта

Цель: подготовить справочник текущего поведения Team Planner, в котором можно
быстро найти ответ «как это работает и почему получился такой результат».
Документация создаётся по существующему проекту: от реализации к аналитическому
описанию, сценариям и правилам. Этот файл — план работы, а не готовая спецификация.

## 1. Принципы

- Описывать фактическое поведение конкретной ревизии проекта.
- Проверять выводы по коду и воспроизводимым сценариям. README и комментарии
  использовать как подсказки, а не как безусловное доказательство.
- Не выдавать пункты TODO и QA-плана за реализованные функции или пройденные тесты.
- Отделять наблюдаемое поведение, принятое требование и обнаруженное расхождение.
  Если поведение выглядит ошибочным, описывать факт и заводить вопрос, а не
  превращать ошибку в согласованное бизнес-правило.
- Писать сначала на языке пользователя; технические детали давать рядом
  отдельным подразделом, когда они объясняют результат.
- Не копировать рабочие данные пользователя: примеры и проверки — синтетические.
- Не менять приложение в рамках документирования; исправления согласовывать отдельно.

## 2. Структура будущего справочника

Точка входа: `docs/product/README.md`. В ней — оглавление, поиск по вопросам,
границы описания, ревизия и дата последней проверки.

| Файл в docs/product/              | Содержание                                                                                                                |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `01-overview.md`                  | Назначение, пользователь, границы продукта, словарь: сотрудник, релиз, очередь, задача, отсутствие, загрузка              |
| `02-scenarios.md`                 | Пошаговые сценарии: начало работы, команда, релизы, задачи, отсутствия, массовые действия, перенос данных, восстановление |
| `03-business-rules.md`            | Очередь и вычисляемые даты, дробные дни, выходные, отсутствия, границы релиза, загрузка и перегрузка; примеры расчётов    |
| `04-interface.md`                 | Карта экранов и диалогов, поля и проверки, состояния кнопок, карточки, индикаторы, подсказки, уведомления, темы           |
| `05-data-model.md`                | Сущности, поля, типы, значения по умолчанию, связи, порядок элементов, вычисляемые поля, версия формата и миграции        |
| `06-storage-and-exchange.md`      | Загрузка и сохранение, серверное и браузерное хранение, импорт/экспорт, демо, снимки, откат, сбои и восстановление        |
| `07-architecture-and-api.md`      | Компоненты и ответственность модулей, путь действия от UI до записи, HTTP-контракты и обработка ошибок                    |
| `08-runtime.md`                   | Запуск Windows, фоновые процессы, порт, повторный запуск, жизнь вкладок, завершение сервера, файлы и диагностика          |
| `09-limitations-and-questions.md` | Ограничения, неподтверждённое поведение, расхождения, вопросы и принятые решения                                          |

README проекта остаётся краткой инструкцией пользователя и получает ссылку
на справочник. `docs/TODO.md` описывает развитие, `docs/QA-PLAN.md` — план проверок.
Справочник ссылается на них, но не дублирует целиком.

## 3. Порядок подготовки

### Этап 1. Зафиксировать исходное состояние и состав продукта

- [ ] Записать commit и значимые незакоммиченные изменения на момент проверки.
      Если описание готовится по рабочему дереву, явно указать это.
- [ ] Прочитать исходники, разметку, стили, запуск, сервер, имеющиеся тесты и документы.
- [ ] Составить перечень всех действий пользователя и подсистем, включая ошибки,
      подтверждения, пустое состояние, демо, миграции и завершение работы.
- [ ] Сопоставить реализованные функции с README и TODO; расхождения вынести отдельно.
- [ ] Создать оглавление и матрицу покрытия: каждый найденный элемент должен
      получить раздел либо явную отметку о пробеле.

Результат: проверенные границы описания, карта функций и список источников.

### Этап 2. Описать сущности и основные сценарии

- [ ] Составить словарь терминов и модель данных по `core/storage.js`,
      обработчикам `features/` и серверной проверке данных.
- [ ] Для каждой сущности описать создание, изменение, удаление, связи
      и последствия действий для других сущностей.
- [ ] Проследить сценарии через интерфейс, изменение состояния, перерасчёт,
      отрисовку и сохранение. Отдельно разобрать отмену и ошибку операции.
- [ ] Уточнить значения по умолчанию, обязательность, ограничения и сообщения
      полей по обработчикам и HTML; различать проверку UI и сервера.

Результат: сценарии и словарь данных, по которым можно понять последствия действия.

### Этап 3. Восстановить правила планирования и отображения

- [ ] Разобрать `core/plan.js`, `core/schedule.js`, `core/dates.js`,
      расчёты загрузки в `core/storage.js` и отображение в `ui/board.js`.
- [ ] Описать источник порядка задач и вычисление начала: отдельно входные
      данные, производные значения и момент перерасчёта.
- [ ] Разобрать дробную длительность, выходные, режим работы в выходные,
      отпуск/больничный, пересечения и выход за границы релиза.
- [ ] Зафиксировать формулы показателей в шапке и по дням; проверить, что
      статус задачи и метки FE/BE меняют в расчётах и отображении.
- [ ] Подготовить таблицы примеров «входные данные → размещение по дням →
      показатели → объяснение» для обычных и граничных случаев.
- [ ] Отдельно проверить поведение при изменении длительности, исполнителя,
      порядка задач, дат релиза и периода отсутствия.

Результат: правила, позволяющие вручную объяснить конкретную доску.

### Этап 4. Описать сохранность данных и работу приложения

- [ ] Проследить стартовую загрузку, выбор хранилища, автосохранение,
      индикаторы, повторные попытки и закрытие вкладки с несохранёнными правками.
- [ ] Описать полный импорт/экспорт, демо, резервные копии, откат и миграции:
      что заменяется, что сохраняется, как проверяются данные, что можно отменить.
- [ ] Для каждого фактического HTTP-маршрута записать метод, запрос, ответ,
      статусы, ошибки и побочные эффекты по `server.js` и клиентским вызовам.
- [ ] Проверить цепочку `start.bat` → VBS → сервер → браузер, выбор порта,
      обнаружение запущенного экземпляра и завершение по сигналам вкладок.
- [ ] Разобрать потерю соединения, некорректный файл и конкурирующие вкладки;
      неизвестное поведение отметить вопросом до проверки.

Результат: техническое описание жизненного цикла и инструкция диагностики.

### Этап 5. Проверить описание на работающем приложении

- [ ] Пройти основные сценарии на изолированных синтетических данных.
- [ ] Сверить примеры расчётов с фактической доской и сохранённым состоянием.
- [ ] Проверить ошибки и граничные случаи, особенно потенциальную потерю данных.
- [ ] Для каждого вывода отметить основание: код, ручная проверка,
      существующий автоматический тест. Не называть чтение кода запуском теста.
- [ ] Зафиксировать окружение и непройденные проверки; не скрывать их за
      общей отметкой «всё проверено».
- [ ] Зарегистрировать расхождения; исправлять текст по фактам, а спорное
      продуктовое решение оставлять открытым до согласования.

Результат: проверенное описание с явными границами достоверности.

### Этап 6. Сделать справочник удобным и поддерживаемым

- [ ] Добавить ссылки из README и перекрёстные ссылки между разделами.
- [ ] Добавить указатель вопросов: «почему задача началась здесь?»,
      «почему загрузка красная?», «что произойдёт при удалении сотрудника?»,
      «куда записались изменения?», «что заменит импорт?», «как вернуть данные?».
- [ ] Убрать дублирование правил: у каждого правила один основной раздел.
- [ ] Проверить ссылки, термины, примеры и полноту матрицы покрытия.
- [ ] Установить правило сопровождения: изменение поведения сопровождается
      обновлением соответствующего сценария, правила, примера и проверки.

Результат: готовый справочник, который можно использовать при работе и разработке.

## 4. Шаблон описания функции

1. **Назначение и точка входа:** зачем функция нужна и откуда вызывается.
2. **Предусловия:** какие данные и состояние необходимы.
3. **Основной сценарий:** действия пользователя и реакция системы по шагам.
4. **Альтернативы:** отмена, пустое состояние, некорректный ввод, сбой.
5. **Правила:** значения по умолчанию, ограничения, формулы и порядок обработки.
6. **Результат:** что видно на экране, что изменилось в данных и когда сохранено.
7. **Пример:** конкретный вход и ожидаемый результат, включая граничный случай.
8. **Основание:** файл и функция, ссылка на проверку, ревизия и дата проверки.
9. **Расхождения и вопросы:** что ещё не подтверждено или требует решения.

Правила и сценарии получают стабильные идентификаторы, например `BR-PLAN-001`
и `UC-TASK-001`, чтобы на них можно было ссылаться из задач и тестов.
В ссылках на код предпочтительны путь и имя функции; номера строк могут устаревать.

## 5. Критерии готовности

- [ ] Все найденные действия и подсистемы отражены в матрице покрытия.
- [ ] По описанию можно пройти основные сценарии без чтения исходников.
- [ ] Все расчётные показатели имеют правило и конкретный проверенный пример.
- [ ] Для изменения и удаления данных описаны последствия и сохранение.
- [ ] Описаны фактические API, формат данных, миграции и жизненный цикл сервера.
- [ ] У значимых утверждений есть источник; пробелы и ограничения видны явно.
- [ ] Реализованное поведение отделено от планов и неподтверждённых требований.
- [ ] Справочник проверен на зафиксированном состоянии проекта и доступен из README.

Подготовку вести последовательно по этапам. Первый законченный срез — сценарий
«создать сотрудника и релиз → добавить задачи и отсутствие → объяснить размещение
и загрузку → сохранить → открыть повторно». Он проверит удобство структуры
до распространения шаблона на остальные функции.
