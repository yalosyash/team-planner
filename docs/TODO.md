- [ ] При возврате узнавать исходный релиз по устойчивому идентификатору

Предложение для первой версии: на время замещения рабочую копию ведёт

## 4. Проверка и установка обновлений приложения

Цель: рядом со статусом сохранения показать кнопку проверки обновлений,
которая предлагает обновиться при любых новых изменениях в отслеживаемой ветке
удалённого репозитория — один коммит или несколько, без ожидания выпуска версии.

Принятые решения:

- Поддержать и папку из архива, и Git-клон.
- Проверка может выполняться автоматически, установка — строго по нажатию
  «Обновить». Пока пользователь не нажал кнопку, файлы приложения не менять.
- После кнопочного обновления Git-клона обычный `git pull` должен оставаться
  работоспособным; состояние Git должно соответствовать установленному коду.

Предлагаемое поведение:

- [ ] Добавить отдельную кнопку рядом со статусом сохранения.
- [ ] Предусмотреть состояния «Проверить обновления», «Проверяем…», «Обновить»
  и «Установлена последняя версия».
- [ ] Проверять обновления при запуске и по нажатию кнопки.
- [ ] При ошибке проверки показывать понятное сообщение и позволять повторить
  попытку; отсутствие интернета не должно мешать работе планировщика.
- [ ] Установку выполнять только по нажатию пользователя.
- [ ] Перед установкой дождаться успешного сохранения данных и создать
  резервную копию.
- [ ] Обновлять файлы приложения с сохранением рабочих данных и резервных копий.
- [ ] При необходимости перезапускать сервер и перезагружать страницу.
- [ ] Продумать восстановление работоспособной версии при неудачной установке.

Предлагаемые способы реализации одного пользовательского действия:

- [ ] Для папки из архива хранить идентификатор установленного коммита,
  сравнивать его с удалённой веткой и по кнопке загружать архив конкретного
  коммита. Учесть, как определить исходную версию у уже скачанных архивов,
  где такого идентификатора ещё нет.
- [ ] Для Git-клона обновлять через Git, синхронно меняя рабочее дерево и HEAD.
  Не заменять отслеживаемые файлы поверх старого HEAD обычной распаковкой архива:
  это создаст локальные изменения и помешает последующему `git pull`.
- [ ] В обычном Git-клоне с чистой веткой использовать обновление только
  fast-forward до проверенного удалённого коммита.
- [ ] При локальных правках, локальных коммитах с расхождением истории,
  неподходящей ветке, detached HEAD или отсутствии Git показать причину,
  почему кнопочное обновление недоступно. Не делать автоматические reset,
  stash или merge и не перезаписывать пользовательские файлы.
- [ ] При обновлении из архива учитывать удалённые и переименованные файлы
  приложения; сохранять `data/`, резервные копии и пользовательские файлы.
- [ ] Загружать и проверять обновление во временной папке до замены файлов;
  предусмотреть применение после остановки сервера и откат при сбое.

Автоматическая проверка только узнаёт о новой версии кода. Применять обновление
или перезапускать приложение без нажатия пользователя нельзя.

Проверить перед завершением:

- Отсутствие обновлений, наличие новой версии и повторную проверку.
- Недоступность сети и ошибку загрузки обновления.
- Успешную установку, перезапуск и сохранность данных/резервных копий.
- Отказ сохранения данных перед установкой и сбой самой установки.
- Для Git-варианта — наличие локальных изменений.
- Обновление на один и несколько коммитов и последующий обычный `git pull`.
- Обновление папки из архива, включая удалённые файлы, без потери рабочих данных.
- Отсутствие изменений файлов приложения до нажатия «Обновить».
